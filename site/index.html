Your routers. Your routing history. Standard files.

bgpviews turns one or two routers into your own small RouteViews: a single binary receives BMP, writes RouteViews-shaped MRT into a plain directory, and leaves a Parquet catalog beside it.

monocle, bgpkit-parser, bgpdump and DuckDB can read the output without a service in the middle. The result is an archive you own, on your own disk.

00 / START HERE

Three ways to get a binary

No build step, no database, no agent to install. Take one file, point a router at it, and the first interval lands on the next UTC boundary.

Static binary or container

Linux is musl, so any distribution 
# from https://github.com/bgpkit/bgpviews/releases
tar xzf bgpviews-x86_64-unknown-linux-musl.tar.gz
./bgpviews --version

# or the image (uid 999 needs a writable root)
docker run -d -p 17901:17901 \
  -v bgpviews-archive:/var/lib/bgpviews \
  -v "$PWD/bgpviews.toml:/etc/bgpviews/bgpviews.toml" \
  bgpkit/bgpviews:latest

# or from source
cargo install --git https://github.com/bgpkit/bgpviews bgpviews

01 / OVERVIEW

The archive public collectors cannot give you

Public archives show what a few hundred routers saw. They cannot show what your routers saw, what your inbound policy dropped, or what your network looked like last Tuesday at 03:00. Building that privately normally means assembling parsers, writers, rotators and a database before the first useful file exists.

bgpviews makes that pipeline one program with one configuration file and one output directory. The archive stays where you run it, written and read locally, with no database server and no second daemon to operate.

Network operators

Keep your own routing history without running a data platform.

Researchers

Build an archive for vantage points that cannot be published.

IXPs

Offer members BGP history without operating a collector service.

Where it fits

bgpviews is a collector you run yourself: it takes BMP from your routers and writes files that existing tools already read. It sits beside the systems you have rather than replacing them. v0.1.6 is released; the v0.x line may still change its on-disk format between releases.

02 / MECHANISM

From BMP stream to readable archive

A router points BMP at the binary. Each client has one listening port and a source-IP allowlist. This boundary matters because BMP has no authentication of its own.

STEP 01 / RECEIVE

Accept BMP frames

The single binary receives router sessions. A raw session journal retains every accepted frame, including Peer Up and Peer Down, so replay is possible within journal_retention_days; the default is 30 and 0 keeps everything.

STEP 02 / SEPARATE

Read the per-peer header

The view is chosen in the configuration and every message's per-peer header is routed into it; frames for another view are counted as unconfigured. Each configured view becomes its own collector named <client>-<view>.

STEP 03 / PUBLISH

Write standard artifacts

RouteViews-shaped MRT, JSON sidecars and a Parquet catalog land in a plain directory for existing tools to read.

Five views remain distinct

  • Adj-RIB-In pre-policy
  • Adj-RIB-In post-policy
  • Loc-RIB
  • Filtered Loc-RIB
  • Adj-RIB-Out (the router's own outbound export)

Pre-policy and post-policy exports are separate collectors, making policy visible as data rather than something inferred later. A record whose view is not configured is counted and left in the journal. It is never written into a different collector.

03 / ON DISK

One directory existing tools already read

The output directory resembles a RouteViews collector. The Parquet catalog is a projection of the segment sidecars and can be rebuilt from them. Tombstones ensure that a deleted file is not later reported as lost.

Schematic archive tree

Fixed layout, one collector per view 
archive/                              # one output directory
├── <client>-<view>/bgpdata/YYYY.MM/ # RouteViews layout, one collector per view
│   ├── UPDATES/updates.…HHMM.gz      # MRT, plus a sidecar JSON per file
│   └── RIBS/rib.…HHMM.gz             # snapshots, only when rib = true
├── coverage/<collector>/<stream>     # ranges: what covers what, and why not
├── sessions/<client>/<epoch>/        # every accepted BMP frame, replayable
├── catalog/                          # rebuildable Parquet projection
│   ├── segments   ├── sessions       #   peer_state, gaps, peers beside them
└── tombstones/                       # a deleted file never looks lost

Paths are the ones the design fixes, and a reader can rebuild everything below `catalog/` from the sidecars and the coverage log. Updates segments use a UTC-aligned cadence, gzip and the RouteViews directory layout, with a JSON sidecar per segment: a 5-minute archive writes 12:00 and 12:05, never 12:03. RIBS/ appears only when snapshots are enabled; they are derived from a live in-memory trie and cost roughly 85 MB per full table, so the default 8-hour cadence is about 255 MB a day per view while a snapshot on every 5-minute update boundary would be tens of gigabytes.

04 / CONTROL PLANE

One TOML file as the control plane

Behaviour lives in one TOML file. SIGHUP re-reads it. In this design the file is the whole control plane and there is no HTTP surface; the CLI is limited to running, inspection, verification and repair.

Configuration contract

Schematic TOML comments 
# bgpviews.toml
# One file is the entire control plane.
[archive]
root = "/var/lib/bgpviews"

[[clients]]
name = "r2"
listen = "0.0.0.0:17901"
allow_from = ["192.0.2.1/32"]  # the router: its address is the only credential
feed = "bmp"

[clients.view]
name = "adj-in-pre"
# cadences default to RIPE RIS:
#   updates every 5 min, whole multiples of it on the UTC clock
#   rib = false; set rib = true for snapshots every 480 min
#
# The view is configured here and the per-peer headers
# of that session are routed into it; frames for another
# view are counted as unconfigured_view.
# Reload with SIGHUP. The file is the control plane.

Start and inspect

Defined commands 
bgpviews check
bgpviews run
bgpviews status
bgpviews verify

A router that cannot export BMP can still be archived: set feed = "bgp" with asn and bgp_id, and the collector peers with it instead of listening for BMP. check prints the neighbour block for that case rather than a BMP target.

check validates the configuration and prints the router snippet and firewall rule to paste. status prints each collector's segment counts, the reasons any segment is partial, the peer baseline and the coverage ranges, including the interval still being written. Separating dead from idle from refused on a thirty-day matrix is designed and not yet released.

That is the minimum a client needs; every other key has a default. Three of those defaults decide what an archive actually does. archive.add_path = "reject" refuses a peer that negotiated ADD-PATH at Peer Up, so set it to "detect" to accept one. archive.journal_retention_days = 30 expires closed session journals, after which the raw frames can no longer be replayed; 0 keeps everything. disk_warning_percent = 90 and disk_critical_percent = 97 are the guards that turn a full disk into a named reason rather than a truncated file.

check also refuses a RIB interval that is not a whole multiple of the update interval: a snapshot comes due only when an update interval closes on a boundary that is also a multiple of it, so any other pair would never fire.

05 / COVERAGE

Coverage is a partition of time, and it is auditable

The archive does not report a status per interval and leave you to guess what the gaps mean. It keeps one ordered list of ranges per collector, and every instant of that collector's life falls in exactly one range. A reader can therefore tell “nothing happened” apart from “nothing was recorded”, which is the question an archive is actually asked.

Two kinds of range, and no third.
RangeWhat it tells a reader
segmentAn MRT file covers this range. A segment may contain zero records, which is how “we were watching and nothing happened” is written: the file exists and its sidecar says records=0.
gapNo file covers this range, and the range names why: no session, a view never observed, a peer that never completed its table, backpressure, a closed session, a removed view.

Ranges are contiguous and append-only. A closed range is never edited, never split and never removed, so a coverage file that disagrees with the MRT files beside it is a verify failure rather than a silent inconsistency.

Three states a segment can carry. Only the first two are publishable.
StatePublished meaning
completeThe range closed at its configured boundary, belongs to one session and one view, its journal is contiguous, and no reason applies. It never claims that loss at the exporter before its socket did not happen.
partialSomething named went wrong: a peer still syncing, a session that ended mid-interval, a restart, a refusal, a disk guard. The reason is in the sidecar, not inferred later.
withheldThe segment failed its own integrity check and sits in quarantine/. Its range stays in the timeline so the attempt is recorded, and no reader treats it as coverage.

A file that is absent, expired on purpose, or failed verification is three different things, and the archive says which: missing, a tombstone, and corrupt.

06 / CLI

Six commands, five for a healthy system

The full command surface. Catalog rebuilding is reserved for disaster recovery; quarantine is the manual override that produces the withheld state above.
CommandPurpose
bgpviews runStarts bgpviews.
bgpviews checkValidates the config and prints the router snippet and firewall rule to paste.
bgpviews statusPrints coverage ranges, segment counts, partial reasons and the peer baseline from the archive.
bgpviews verifyReconciles the catalog against disk.
bgpviews rebuild-indexRebuilds the catalog. Disaster recovery only.
bgpviews quarantine --config FILE --path FILE --reason TEXTWithholds one artifact and records why, so the range reads as withheld rather than lost.
07 / CATALOG

Inspect the projection with DuckDB

The catalog contains segments, sessions, peer_state, gaps and peers. Because it is Parquet in a plain directory, DuckDB can read it without a bgpviews service.

Catalog inspection query

One part per day, one directory per month 
SELECT * EXCLUDE (part_seq, row_version)
FROM read_parquet('archive/catalog/segments/**/*.parquet')
QUALIFY row_number() OVER (
    PARTITION BY collector, stream, interval_start, ordinal
    ORDER BY part_seq DESC, row_version DESC
) = 1
ORDER BY interval_start
LIMIT 20;

These are the columns v0.1.6 writes, one row per segment, with a part written per day and a directory per month. Writing only ever appends a part, so a rebuilt catalog holds several revisions of the same segment and part_seq says which one is newest: that is what the QUALIFY clause keeps. The sidecar beside each MRT file stays the authority for what the file holds and why state is partial; the catalog is a projection of it and rebuild-index can regenerate it. Use verify to reconcile the catalog against disk.

08 / LIMITS

What it does not do yet

These are hard limits of v0.1.6, not roadmap wishes. A reader deciding whether this fits should read them before the archive layout above.

  1. A peer that negotiated ADD-PATH is refused

    At Peer Up, by default: archive.add_path = "reject". Set it to "detect" to accept one and decide the BGP4MP subtype per message. A message that fits both readings is skipped and named add_path_ambiguous in the segment's reasons.

  2. Only FRR has a router snippet and a capture behind it

    check prints an FRR bmp targets block for a BMP client, or a neighbour block for a BGP client. For Junos, IOS-XR, SR OS and EOS there is no snippet and no capture, so nothing about them is tested.

  3. Loc-RIB views have no real capture

    A Loc-RIB view comes from RFC 9069 type 3 frames, one instance per client. The lab that produced it is synthetic: no production router capture exists yet, so treat Loc-RIB output as less proven than adj-in-pre.

  4. One writer per archive root

    A second run against the same directory refuses to start. There is no shared-ownership mode and no remote writer, because the archive's coverage guarantee depends on a single writer knowing every boundary.

  5. Session journals expire after 30 days

    journal_retention_days defaults to 30, so raw-frame replay stops covering an interval once that window passes. Set 0 to keep every journal, at the cost of the disk it uses.

  6. The on-disk format may still move

    Every release in the v0.x line may change the archive format and the catalog schema. Do not build a permanent store or a long-lived parser against 0.1.x; wait for 1.0.
