# bgpviews: a self-hosted BGP archive

Status: **v1.0-rc1**, frozen 2026-11-14 after eighteen adjudicated review rounds. Nothing is implemented yet; this document is the contract an implementation is written against.


## 1. Positioning and product boundaries

bgpviews turns one or a few routers into a small private RouteViews-style archive. A router exports BMP to one binary on the operator's machine; the binary writes MRT files, a Parquet catalog, and the recovery metadata needed to trust them into one plain directory. monocle, bgpkit-parser, bgpdump, DuckDB, and other existing tools can consume the artifacts without a service or glue pipeline.

The users are network operators keeping their own history, researchers using private vantage points, and IXPs providing member history. The project is a toolchain: `bgpviews-core` is a library and `bgpviews` is a thin binary, so another application can call the engine in process. Support is best effort through GitHub issues, with no SLA.

What it produces is files on disk plus a catalog beside them. The process reads exactly one configuration file and answers five commands, and those commands cover running, inspection and repair. An operator may configure an optional publisher that copies selected artifacts to a local path or an S3 destination; with no publisher configured, nothing leaves the machine. Input arrives as BMP from a router or as a plain BGP session from a router that cannot export BMP, and section 4 states the difference.

## 2. Acceptance bar and source basis

Plug and play means that a new user can install one binary with no runtime dependency beyond libc, run `bgpviews check --config bgpviews.toml`, paste the displayed router and firewall configuration, run `bgpviews run --config bgpviews.toml`, and within fifteen minutes see a live session and one finalized segment in `bgpviews status`. The user then runs `monocle parse` on one updates file and on each file expanded from an hour-long shell glob. monocle accepts one file path, not a directory (`refs/monocle/src/bin/commands/parse.rs:19-25,119-128`). This sequence is the v1.0 release gate.

Protocol behavior in this document is derived from the checked-out sources, not from memory. The source baseline is bgpkit-parser commit `8e9f83c69606aaa651b83d33e56f77d13b93b771`, focl commit `3a6ff28611a43b0e2f0e2d2a2c0a138ee78f21e5`, and monocle commit `cf24c610592460d8d7454f39c6c0ee38ca68abc2`. RFC 7854 sections 3.3, 4.2, 4.10, and 5, RFC 9069 sections 4.2, 5.1, 5.2, and 5.4.1, and RFC 8050 sections 3 and 4 are the normative companions. If this text and the cited parser differ, this text is wrong and must be re-derived before implementation continues.

The archive reuses focl's raw-PDU BGP4MP envelope approach and TABLE_DUMP_V2 work where applicable, not its listener or archive control flow. In particular, raw BGP4MP output requires peer and local addresses of one family (`refs/focl/src/archive/snapshot.rs:45-87`). Measured public files establish only an order of magnitude, not a capacity claim: on 2025-11-12 the sampled RouteViews updates files were 1,696,029 and 9,258,589 bytes and the sampled RIB was 85,440,170 bytes (`evidence/routeviews-file-sizes.txt`). ADD-PATH and journal overhead need their own measurements.

## 3. Identities and clocks

A `client` is one configured feed source with one listener and source allowlist, and its `feed` is `bmp` or `bgp`. The feed is a property of the client because it decides how a record is read; changing it means a new client name, and every segment records the feed it came from so a reader never has to guess from a path. `clients/<client>/next_epoch` holds the next unused `u64`; its value becomes `session_epoch` and is incremented and fsynced before a connection is accepted. Recovery uses the greater of that value and one plus the largest session directory epoch. Only one session per client is active; a replacement closes the old one before allocation.

A `peer_key` is `(peer_type, peer_distinguisher, peer_ip, peer_asn, peer_bgp_id)` for types 0, 1 and 2, and `(peer_type, peer_distinguisher, peer_bgp_id, filtered, open_family_set)` for type 3. The type 3 key is longer for a reason: RFC 9069 section 6.1.1 lets several emulated peers of one Loc-RIB instance share distinguisher and BGP ID, and section 5.1 zero-fills the address, so two instances differ only by their filtered flag and by the families their fabricated OPENs declare. Both are in the key, so a `loc-rib` peer and a `loc-rib-filtered` peer cannot collide, and no ordinal is assigned anywhere: the identity is a function of the Peer Up itself, which is what makes live processing and replay agree. A `peer_up_generation` is a `u64` scoped to `(session_epoch, peer_key)`, starting at 1 and incrementing on each Peer Up for that key. A repeat Peer Up for a key that is already active is a new generation, not an error, because that is how a re-established emulated peer announces itself. A new generation clears only the `(afi, safi)` objects its OPEN declares, never every object of the peer. A Peer Up that reuses `(peer_type, peer_distinguisher, peer_ip)` with a different AS or BGP ID closes the session with `peer_state_error`, because silently treating it as the same neighbour would merge identities.

A `view` is the collector-local routing domain named in section 4. A `collector` is `<client>-<view>`; client names contain only lowercase ASCII letters, digits, and underscore, so the final hyphen before a known view name is unambiguous. A peer generation can feed several views at once.

`receive_at` is collector UTC captured for a complete BMP frame; it controls intervals, gaps, RIB cutoffs and replay order. A collector has exactly one time base for its whole life. Assignment never moves backwards: `clients/<client>/receive_watermark` holds the last assigned value and is rewritten inside the same commit that fsyncs each journal batch, and startup recomputes it as the greater of the persisted value and the last journaled receive time before a socket is accepted. A frame whose raw reading is below the watermark by at most `clock_step_back_tolerance` is assigned `watermark + 1µs`, journals a `clock_step_back` event, and gives its segment `receive_time_anomaly`. A regression larger than that closes the session with `clock_step_back` and the client stays unusable, because accepting a lower time base would put new records inside intervals that are already closed. The remedy is explicit and it is the operator's: fix the clock, or archive that source as a new client name, which starts a new collector with its own time base. A forward jump larger than `clock_step_forward_tolerance`, measured by comparing the wall-clock delta against the process's monotonic elapsed time so that an idle session is not a jump, closes the session with `clock_step_forward`, and the wall-clock range it skipped becomes a `no_session` gap. `router_at` is the BMP per-peer timestamp copied into MRT and the journal; a `bgp` feed has no per-message router timestamp, so there `router_at` is the frame's `receive_at` and the skew and anomaly rules apply only to a `bmp` client.

## 4. Protocol fact table and view routing

The parser defines peer types 0, 1, 2, and 3 as Global, RD, Local, and LocalRib (`refs/bgpkit-parser/src/parser/bmp/messages/headers.rs:188-207`). Their flag layouts are not interchangeable.

| Peer type | Flags that exist | AS width and Peer Up Local Address | View and refusal rule | BGP4MP output and ADD-PATH authority |
|---|---|---|---|---|
| 0, Global Instance | `V=0b1000_0000`: peer address is IPv6 when set; `L=0b0100_0000`: post-policy Adj-RIB-In when set; `A=0b0010_0000`: legacy 2-byte AS_PATH when set; `O=0b0001_0000`: Adj-RIB-Out when set (`headers.rs:209-280`). | A selects 16-bit AS_PATH when set and 32-bit otherwise (`headers.rs:179-185,257-269`). Peer Up Local Address is the monitored BGP session's local address, not the BMP socket address (`peer_up_notification.rs:14-20`; RFC 7854 section 4.10). | O=0 selects `adj-in-pre` or `adj-in-post` from L. O=1 is named `adj-out` and follows the unconfigured-view rule below. A nonzero peer distinguisher is `peer_state_error`. | For archived Adj-RIB-In records, subtypes are 1 or 8 with A set and 4 or 9 with A clear (`models/mrt/bgp4mp.rs:41-56`). ADD-PATH is per Peer Up generation and AFI/SAFI: the sent OPEN must offer Receive or SendReceive and the received OPEN must offer Send or SendReceive (`capabilities.rs:342-368`). |
| 1, RD Instance | The parser applies the same V, L, A, O layout as type 0 (`headers.rs:311-360`). | A follows type 0. Peer Up exposes the same Local Address and OPEN fields, but no envelope is built. | Refused with `unsupported_peer_type` before any MRT output for that message. RD and VRF archiving are non-goals; no global collector is selected. | None. The raw message is journaled, the open configured segments become partial, and the session closes. |
| 2, Local Instance | The parser applies the same V, L, A, O layout as type 0 (`headers.rs:311-360`). | A follows type 0. Peer Up exposes the same Local Address and OPEN fields, but no envelope is built. | Refused with `unsupported_peer_type` before any MRT output for that message. Local instances are non-goals and are never folded into global Adj-RIB-In. | None. The raw message is journaled and the session closes as for type 1. |
| 3, Loc-RIB Instance | Only `F=0b1000_0000` exists and means filtered Loc-RIB. V, L, A, and O do not exist in this layout; the other bits are reserved (`headers.rs:282-297`; RFC 9069 section 4.2). | AS width is always 32-bit regardless of the flag byte (`headers.rs:179-185`; `route_monitoring.rs:19-23`). Peer Address and Peer Up Local Address are zero-filled (RFC 9069 sections 5.1 and 5.2). | Distinguisher zero and F clear select `loc-rib`; distinguisher zero and F set select `loc-rib-filtered`. A nonzero distinguisher denotes a non-global instance and is refused with `vrf_not_supported`. | Subtypes are 4 without ADD-PATH and 9 with ADD-PATH. The fabricated sent OPEN's ADD-PATH capability presence for the AFI/SAFI is authoritative; its Receive/Send intent is ignored, and the received OPEN must repeat it (RFC 9069 section 5.2). Peer and local MRT addresses are both `0.0.0.0`. |

The mirror-image rule applies to a type 3 Route Monitoring message, which carries no OPEN either, and it is decided in two steps.

The message's family set is read from every place an NLRI can appear: classic IPv4 unicast announced and withdrawn NLRI, plus the AFI and SAFI of the MP_REACH and MP_UNREACH attributes when present, because one UPDATE can carry both, for example an IPv4 withdrawal and an IPv6 announcement. An end-of-RIB marker would otherwise produce an empty set, which every declared set contains, so EoR is classified before selection, and the classification is per family and requires that family to carry no NLRI in the same message. An EoR is exactly the message the parser's end-of-RIB predicate accepts and nothing else (`refs/bgpkit-parser/src/parser/bgp/messages.rs:674-715`): an UPDATE with no announced or withdrawn NLRI and an attribute list that is either empty, which is the EoR of IPv4 unicast, or exactly one MP_UNREACH_NLRI naming a single family, which is the EoR of that family. The predicate returns false for any other attribute list, including an MP_UNREACH beside another attribute, so such a message is a route update and its family set is read the normal way. A message that is not an EoR but carries no NLRI in any family has an empty family set, and an empty set selects no instance: it takes the `capability_mismatch` outcome below. The document never grants EoR meaning to a shape the parser would reject, and it never leaves a non-EoR message with no family unattributed.

Candidates are the active generations of this view whose per-peer header tuple `(distinguisher, bgp_id, filtered)` equals the message's, restricted to instances whose `peer_up_generation` is the current one. Among those, the instance must be the unique one whose `open_family_set` contains the whole family set. Exactly one match is the target. More than one is `loc_rib_peer_ambiguous` and the message is refused, because applying it to each candidate would insert another instance's routes into a trie that never received them and splitting it would mean re-encoding the PDU. Zero matches is `capability_mismatch`: the message is journaled, no state row is created, and the affected view's open segment is marked `capability_mismatch` and cannot be published `complete`. This is the single outcome for the case, and it replaces both the older rule that created a state row and the older rule that only journaled.

A `bmp` type 0 feed is unaffected, because one message always belongs to one monitored peer and the record's AFI describes that peer, not the NLRIs inside.

A type 3 Peer Down carries a per-peer header and, for reason 6, an optional VRF or table name, but never a family set and never an OPEN, so the instance it belongs to cannot always be derived. The rule is therefore explicit: when the header's `(distinguisher, bgp_id, filtered)` matches exactly one active instance, that instance closes; when it matches several, every match closes, each affected view is marked `partial` with `loc_rib_peer_ambiguous`, and `status` reports the count. Closing more than the router meant is visible and correctable by the next Peer Up, and it removes only paths a live instance will re-announce; the asymmetry with Route Monitoring is deliberate, because an over-closed trie loses data that returns, while an over-applied message inserts data that never existed in that instance.

The per-message Route Monitoring header selects the view on every record. Pre-policy and post-policy streams may be multiplexed on one BMP session (RFC 7854 section 5), so a record in one view says nothing about whether the other view stopped. There is no `view_switch` state, no remembered "collector it left," and no flag-triggered segment close. Peer Down and session close affect all views of that peer or session; an idle view is not inferred to be dead.

A Route Monitoring record for a valid but unconfigured view has exactly one outcome: its complete BMP frame remains in the raw session journal, `unconfigured_view{client,view}` increments, and it produces no MRT record, no RIB state, no partial reason, and no file. It is configuration-based exclusion, not an ingest failure. There is no `dropped_record_count` column. A configured-view record that cannot be encoded is not excluded: it follows the failure rules in sections 9 and 13.

Peer Up supplies both OPEN messages and Local Address (`refs/bgpkit-parser/src/parser/bmp/messages/peer_up_notification.rs:14-20,54-92`), and OPEN carries My AS and the BGP identifier (`refs/bgpkit-parser/src/models/bgp/mod.rs:155-164`). BMPv3 has no per-message ADD-PATH flag. The current parser nevertheless calls `parse_bgp_message(data, false, asn_len)` on the Route Monitoring path (`route_monitoring.rs:14-29`), so #363 must provide generation-scoped, per-AFI/SAFI decoding before the ADD-PATH acceptance test can pass. bgpviews does not guess path identifiers or fork around that parser behavior.

For type 0, expected families are IPv4 unicast plus the received OPEN's multiprotocol families. For type 3, expected families are those in the fabricated OPEN. A Route Monitoring message outside that set takes the one `capability_mismatch` outcome defined in section 4.2 and is never silently dropped: no instance state row is created and the message is journaled; the refusal is counted in the view-level state for the session, and it marks any open `segment` range so that range cannot be published `complete`. Section 5.4 states where that counter lives and why a refusal never removes coverage.

### The BGP peering feed

Some routers cannot export BMP: old code, a managed device, a lab VM. A client may therefore be configured with `feed = "bgp"`, in which case bgpviews accepts an ordinary BGP session from that router and archives what the neighbour advertises to it.

- **One view only.** A BGP session carries the router's chosen path, so the collector is `<client>-adj-in-pre` and no other view block is accepted for a `bgp` client. There is no post-policy, Loc-RIB or Adj-RIB-Out variant of this feed, because the protocol carries none of those stages.
- **Peer identity** is the single neighbour: peer IP, peer AS and peer BGP ID from the OPEN, with `peer_up_generation` replaced by the BGP session generation. `peer_state` still records dump start and end-of-RIB per AFI/SAFI, where end-of-RIB is the BGP EOR marker.
- **Encoding.** The received UPDATE is copied unmodified and wrapped in BGP4MP with the subtype chosen by the AS width negotiated in the OPEN: 4 or 9 for a four-octet speaker, 1 or 8 for a two-octet one, with the ADDPATH variant only when both sides negotiated it. `local_as` is the client's configured AS, `local_ip` and `peer_ip` are the TCP endpoints of the BGP session, and interface index is 0 as for BMP. The same representability rule as section 10 applies to this feed: in a two-octet session `local_as` above 65535 is written as AS_TRANS with the true value in `local_as_true`, and a peer whose AS does not fit the negotiated width closes the session with `as_width_unrepresentable`. `router_at` is the frame's `receive_at`, because BGP carries no per-message timestamp, and no skew rule applies to this feed.
- **The collector never announces a route.** It sends its own OPEN and KEEPALIVE and nothing else: no prefixes, no default, no route refresh requests that would force a re-dump. It also never acts as a route server and has no outbound policy.
- **Guards.** Optional `md5` for the session key, and `max_prefixes` as a hard ceiling per AFI/SAFI; exceeding it closes the session with `max_prefixes_exceeded` rather than archiving a partial table as if it were complete.
- **End of initial table.** A BGP feed treats the EOR marker as the only completion signal, exactly as the BMP feed does. A peer that never sends one leaves every interval it writes records in `partial` with `peer_syncing_at_open`, and every interval it writes nothing in an empty segment carrying the same reason. There is no timeout option, because a timeout would be a guess dressed as an observation. That is the honest state: there is no timeout option, because a timeout would be a guess dressed as an observation.

**Failure semantics are unchanged.** A BGP session drop writes `session_ended`, closes the open segments as partial and opens a gap, exactly as a BMP session loss does. It never synthesizes withdrawals, and a reconnecting session starts a new generation with an empty trie.

The rest of this document is written for BMP, and the mechanisms it describes are feed-neutral: the session journal, the segment transaction, the catalog projection, the coverage states and the RIB derivation all take records from either feed. Where a rule names a BMP message it applies only to a `bmp` client.

## 5. Directory layout and deterministic names

One directory is the archive. The RouteViews-shaped collector trees contain only published MRT and their sidecars; temporary, quarantined, session, and state artifacts never masquerade as RouteViews data.

```text
archive/
  edge1-adj-in-pre/bgpdata/2026.11/UPDATES/updates.20261114.1200.gz
  edge1-adj-in-pre/bgpdata/2026.11/UPDATES/updates.20261114.1200.gz.json
  edge1-adj-in-pre/bgpdata/2026.11/RIBS/rib.20261114.1200.partial.gz
  edge1-adj-in-pre/bgpdata/2026.11/RIBS/rib.20261114.1200.partial.gz.json
  clients/edge1/next_epoch
  clients/edge1/receive_watermark
  config/<config_sha256>.toml
  sessions/edge1/0000000000000042/session.json
  sessions/edge1/0000000000000042/journal.0.bin
  sessions/edge1/0000000000000042/journal.1.bin
  sessions/edge1/0000000000000042/peer_state.log
  gaps/edge1-adj-in-pre/<gap_id>.json
  tombstones/<collector>/<segment-file-name>.json
  transactions/<transaction_id>.json
  work/<transaction_id>/...
  quarantine/<transaction_id>/...
  catalog/segments/2026.11/20261114.000001.parquet
  catalog/sessions/2026.11/20261114.000001.parquet
  catalog/peer_state/2026.11/20261114.000001.parquet
  catalog/gaps/2026.11/20261114.000001.parquet
  catalog/peers/2026.11/20261114.000001.parquet
```

The MRT base name is `updates.YYYYMMDD.HHMM` or `rib.YYYYMMDD.HHMM` in UTC. Updates use the configured interval start; a RIB uses the minute containing its exact receive cutoff, including an immediate RIB. Compression is gzip from the repository's locked `flate2` version, level 6, MTIME 0, no original-name field, and OS 255. A first segment is `<base>.gz` or `<base>.partial.gz`; later segments use `<base>.2.gz` or `<base>.partial.2.gz`. The sidecar appends `.json`. Thus `updates.20261114.1200.partial.2.gz` is the second partial updates segment in that interval.

Ordinals are allocated per `(collector, stream, interval_start)` for updates and `(collector, stream, name_minute)` for RIBs by scanning published, quarantine, and transaction records and taking the maximum plus one, with no distinction between the three: an ordinal that ever appeared on disk is never handed out again. Each segment belongs to one session epoch. Third-party discovery of `.partial` and ordinal suffixes is UNVERIFIED; monocle is tested on actual paths and the catalog is authoritative inventory.

All JSON sidecars use schema version 1, UTF-8, lexicographically sorted object keys, no insignificant whitespace, integer UTC seconds plus integer microsecond fields, and one trailing newline. Arrays whose order is not otherwise semantic are sorted by their full keys. Hashes are lowercase SHA-256 hex over the exact bytes of the named artifact. Relative paths use `/` and may not escape the archive root.

### 5.4 The coverage timeline

Coverage is a partition of time, kept per `(collector, stream)`, and this section is the only place that defines it. A range carries exactly one of two kinds:

| kind | what it asserts |
|---|---|
| `segment` | records for this range are in the named MRT file, addressed by `session_epoch` and `ordinal`; a segment may contain zero records, which is how "we were watching and nothing happened" is written |
| `gap` | no MRT file covers this range, and the reason says why |

There is no third kind. A healthy but silent period is an empty segment, not a distinct kind: an updates file with no records is a real RouteViews artifact, it is written, and its sidecar says `record_count=0`. That single change removes the case that kept breaking, because the writer always knows what to open at a boundary.

Four invariants hold, and `verify` checks them:

1. **Contiguity.** The first range is created by an `OPEN` line at the collector's first start, so there is no undefined "first observation": a collector that never completes a Peer Up still has a first range. Every later range starts where the previous one ended. Exactly one range has `end = null`, at all times and in every state: a removed view leaves an open `gap`, it never ends the timeline.
2. **One log, four line types.** The timeline lives in one append-only file and is changed by nothing else:
   - `OPEN(T, kind, reason?)` creates the first range of an empty file. It is used once per timeline, at the first start, and never again.
   - `TRANSITION(T, kind, reason?, segment?, carried_reasons?)` closes the tail at `T` and appends a successor starting at `T`.
   - `ANNOTATE(range_id, reason)` adds a reason to the open `segment` range.

   There is no fourth line and no retirement line. Every close boundary in this document is the `T` of a `TRANSITION`, so no boundary can exist that the log cannot express, and every timeline has exactly one open range for its whole life, which is what makes contiguity checkable without exceptions.
3. **No overlap, no hole.** No two ranges overlap, so no range is covered twice, and contiguity means none is left over.
4. **State is borrowed, not asserted.** A range line records placement and identity; a `segment` range's `state` is read from its sidecar at read time, never frozen in the line. A segment that is quarantined or rebuilt as `partial` after its coverage line was written therefore needs no rewrite of the timeline: the sidecar is the artifact of record and the coverage line only says where the artifact belongs.

The complete list of calls follows. Each states the `T` and the successor.

- **First start.** `OPEN(T_start, gap, no_session)`. A collector begins as a gap, because nothing has been written yet. This is also the restart form when the file is absent or zero length, so a crash before the first `OPEN` cannot leave a collector with no timeline: `OPEN(T_start, gap, writer_restart)` covers it. A file whose only defect is an invalid final line is a torn append: recovery truncates it at that line and continues, which is the ordinary crash case. Every other failure is `coverage_unreadable` and `run` refuses to start: an invalid line that is not the last one, a valid line followed by garbage that is not a single partial line, or a file that does not end at a line boundary with a valid CRC. Appending to a timeline with unknown history would create a second partition of the same time and no later check could tell which one was true.
- **Interval rollover, on the updates stream of that `(collector, stream)`.** `TRANSITION(T_boundary, segment, ordinal next)` while the collector can write; otherwise `gap` with the applicable reason. A RIB stream never rolls at an updates boundary. The successor is `segment` even though it has no records yet, because the file is opened at the boundary and records are appended as they arrive. A segment range that closes with zero records is closed normally and has an empty MRT file and a sidecar with `record_count=0`; `verify` requires the file to exist and be zero bytes of records, not that it be absent.
- **First record into a `gap` range.** `TRANSITION(T=record.receive_at, segment)`. A record closes a gap whatever its reason was, so a record and a `peer_syncing_at_open` gap can never describe the same instant: the transition is the later of the two facts.
- **A peer reaches `synced` while the tail of that collector's updates stream is a gap.** `TRANSITION(T=first sync instant, segment, carried_reasons?)`. Sync has no meaning for a RIB stream, which is cut at its own cutoffs, so this call never opens a RIB range. This is what keeps a silent but healthy view out of a gap without a third kind: from the moment the view has a synced peer, the collector can write, so it writes a segment even when that segment ends up empty.
- **Record into the tail `segment`.** No line: the record is appended to that range's file and the range's `end` stays `null`.
- **Session end.** `TRANSITION(T=session_end, gap, no_session)`.
- **Collector that cannot write** (no session, view never observed in the session, no peer of that view ever reached `synced`, backpressure, disk-critical, journal expired). `TRANSITION(T=when the condition became true, gap, reason)`. These states are nothing special: they are the reason field of a call the writer was making anyway.
- **`gap_max_age` expiry.** `TRANSITION(T=expiry, gap, same reason)`, so accounting stays continuous.
- **Restart, tail present.** `TRANSITION(T=max(tail.start, last_durable_receive_at + 1µs), gap, writer_restart)`. `last_durable_receive_at` is the greatest `receive_at` among records that survived in the journal after torn-tail handling, and `0` when none did. The maximum is what makes `T` legal even when a transition opened the tail after the last record, which is the case after a session end or a first-record transition near the end of the log.
- **View removal by reload.** `TRANSITION(T=reload instant, gap, view_removed)`. The timeline keeps an open gap, because time keeps passing for a collector that no longer records. Re-adding the view later is `TRANSITION(T=re-add instant, gap, no_session)`, so the interval between removal and re-add is covered by the `view_removed` gap and not by a hole.
- **RIB cutoff.** `TRANSITION(T=cutoff_receive_at, segment)` when the RIB was produced, `gap` with a RIB reason when it was not. A RIB range is opened at a cutoff and closed by whatever closes it next, exactly like an updates range; its bounds are not a pair of cutoffs, because a session end or a restart can close it first.
- **Refusal of a message the operator asked for.** If the tail is a `segment`, `ANNOTATE(tail, capability_mismatch)`. If the tail is a `gap`, there is no artifact to annotate, so the reason is added to the view's `pending_reasons` in `sessions/<client>/<epoch>/view_state.log`, which is a frame log with the same framing and CRC as `peer_state.log`, written and fsynced before the refusal is acknowledged. The next `TRANSITION` that opens a `segment` for that view copies those reasons into `carried_reasons` and records `carried_through_seq`, the greatest `view_state.log` sequence it consumed. There is no separate clear step: replay ignores any pending entry whose sequence is at or below the greatest `carried_through_seq` in the coverage log, so one durable append both carries the reason and retires it, and a crash before or after that append yields the same result. The sequence is per `(client, view)` and continues across session epochs, so a refusal recorded in one epoch is still carried by a segment opened in the next. A refusal is therefore never lost, and it never annotates a range that has no reasons field.

A `segment` range's `state` is read from its sidecar and is one of `complete`, `partial`, or `withheld`. Only `complete` and `partial` are publishable. A quarantined segment leaves a `withheld` range in the timeline: the attempt to cover that time is a fact worth keeping, but the range names an artifact in `quarantine/` and no reader may treat it as coverage. Section 5.5 states the three states and the predicate for each, once. RIB completeness is a separate predicate on a different artifact and is named `rib_complete` wherever it is used, so a RIB can never be described by the segment predicate.

A view is **observed** in a session when at least one Peer Up for that view was received in that session. Observation is a property of the session, not of the range, so a later silent range in the same session is still observed, and a silent observed session is written as an empty segment rather than a gap.

### 5.5 The coverage file

`coverage/<collector>/<stream>.jsonl`, append-only, one line per `OPEN`, `TRANSITION`, or `ANNOTATE`. Each line is one JSON object, then one space, then the CRC32C of that object's bytes as exactly eight lowercase hex digits, then `\n`, so framing is byte-exact and a torn append is detectable without guessing where the next record starts. Eight hex digits are required because CRC32C is 32 bits; a shorter field cannot hold it. A reader ignores any line whose CRC does not validate, and recovery truncates the file at the first invalid line. A line becomes authoritative when its `fsync` returns, which is before any artifact that depends on it is published. A reader cannot tell a durable line from a written one, so the design does not claim it can: it reads every CRC-valid line and `verify` reports a `lost_append` note when the coverage log is shorter than the ranges and sidecars that exist, which is the only observable consequence of losing an append. Each `TRANSITION` line carries the range it closed and the range it opened, so one line is one atomic change and a reader never sees half a transition. The line is fsynced before the MRT publication that depends on it, and recovery discards a torn last line the way the journal does; the surviving prefix is the timeline, so contiguity and single-kind hold after a crash without a repair pass.

`verify` checks the log against the sidecars in both directions. A closed `segment` range must name a final sidecar and every final sidecar must be named by exactly one closed range. Two windows are not failures and are reported as notes instead: an open range names its transaction, because its sidecar does not exist yet, and a closed range whose transaction is `finalized=true` but whose final sidecar rename has not happened is `pending`, which is the ordinary state between step 2 and step 3 of finalization. The ranges must be contiguous with no overlap, the records of each segment other than its `late_arrival` count must fall inside the range it was placed in, and the reasons recorded by `ANNOTATE` plus the reasons carried at open must be a subset of the sidecar's `partial_reasons`. The reverse direction is deliberately not an error: recovery may add a reason to a sidecar that the log never recorded, which is how a segment rebuilt as `partial` with `writer_restart` after its range closed is represented without rewriting a closed range. `verify` reports such a reason as a note, so the difference is visible and not silently tolerated. A record outside its range's bounds is legal only up to the sidecar's `late_arrival` count, which is what makes the late-placement rule checkable rather than assumed.

A `segment` range's state, and the only definition of it in this document, is:

- `withheld` when the sidecar says `state=withheld`. The artifact is in `quarantine/`, it is not publishable, and its range stays in the timeline as a record of the attempt.
- `partial` when the sidecar is published and any of these holds: it did not close at its configured receive-time boundary; it belongs to more than one session epoch or more than one view; its journal range is not contiguous; it carries at least one `partial_reasons` entry; or a `peer_state` object active at the range start in the same epoch, generation and view was not `synced`, or was `synced` without an EoR at or before the range start.
- `complete` otherwise.

Every failed condition above has a named reason already, which is why the predicate can be written as a list of conditions and a list of reasons without the two drifting: `peer_syncing_at_open` covers the not-synced case, `journal_corrupt` covers a non-contiguous journal, and a close that did not happen at the configured boundary carries the reason that caused it, which is one of `session_ended`, `writer_restart`, `backpressure`, `disk_critical`, `config_changed`, `view_removed`, or `io_error`. A condition with no reason is a defect in this table, not an exception in the code.

One archive root has one writer. `run` and `rebuild-index` take an exclusive lock on `archive/.lock` for their whole lifetime, and a second writer on the same root exits with `writer_conflict` rather than racing on scan-based ordinal allocation or on catalog replacement. The read-only commands take no lock at all, because every artifact they read is published by an atomic rename. The catalog carries a generation manifest: `rebuild-index` writes its parts, then atomically renames `catalog/GENERATION` to a small file listing exactly the parts of that generation, and a reader reads `GENERATION` first and then only the parts it names. A scan therefore never mixes an old part with a rebuilt one, rebuild never rewrites or deletes a part that a reader may be holding, and a reader never blocks ingest. A lock whose holder is gone is reported for operator removal, never broken automatically, because two writers on one archive is the one failure that cannot be repaired from the sidecars afterwards.

## 6. The session journal and persisted `peer_state`

The session journal, not the updates MRT lane, is the ordered record of BMP events. It is a sequence of parts, `sessions/<client>/<epoch>/journal.<n>.bin` numbered from 0, and a new part starts when the current one reaches `journal_max_bytes` or `journal_rotate_interval`, continuing the sequence with no gap; `session.json` lists the parts in order. Each part starts with the eight-byte magic `BGPVJNL1`. Each frame after the magic contains, in network byte order: `sequence:u64`, `receive_seconds:i64`, `receive_micros:u32`, `kind:u8`, `payload_length:u32`, `payload`, and `crc32c:u32` over the frame fields before the CRC,  Sequence starts at 1 and has no gaps. Kind 0 is one complete raw BMP message including its six-byte common header. Kind 1 is a canonical JSON local event with exactly `event`, `reason`, `raw_receive_seconds`, and `raw_receive_micros`; unused fields are null. Kind 2 is one complete BGP message received on a `bgp` feed, preceded in the payload by its four-byte length-prefixed session identity. Kind 3 is a BGP session event whose JSON payload carries the session generation, both endpoints, both OPENs verbatim including their capability TLVs, the negotiated AS width and ADD-PATH modes, and the reason it was written; `session_up`, `session_eof` and `session_error` are its events. Replay therefore reconstructs a BGP feed from kinds 2 and 3 exactly as it reconstructs a BMP feed from kind 0, and no rule in this document depends on a message source that is not in the journal. Events are `session_end`, `backpressure`, `writer_restart`, `disk_critical`, `config_changed`, `receive_time_anomaly`, `late_arrival`, `clock_step_back`, and `clock_step_forward`.

Every accepted BMP message is journaled: Initiation, Peer Up, Peer Down, Route Monitoring, Statistics Report, Termination, and any refused message with a per-peer header. The updates MRT lane still contains only copied BGP UPDATE PDUs inside BGP4MP envelopes. Replay opens sessions in epoch order and frames in sequence order. It never merges Peer Up or Peer Down from MRT, because those messages are not BGP UPDATEs and are deliberately absent from that lane.

Ingest collects complete frames into a bounded byte batch, assigns their sequence and receive timestamps, writes and fsyncs that journal batch, and only then parses, routes, writes MRT, or mutates a RIB. `journal_batch_bytes` and `journal_commit_interval` bound the batch; a full batch commits immediately. A failure before journal fsync means the batch was never accepted and the socket is not read further. A failure after journal fsync is recoverable by replay. This write-ahead order costs an additional raw copy of BMP, retained for `retention_days_raw`, and is the explicit price of crash and Peer Up/Down replay. The transaction record for an interval is written and fsynced before the first frame assigned to that interval, so no journaled frame is left without an owner; at startup any journal range past the last recorded transaction is adopted as `finalized=false` and rebuilt as partial with `writer_restart` rather than becoming a silent hole.

`peer_state` is a persisted event log at `sessions/<client>/<epoch>/peer_state.log`, not a mutable latest-value row. It starts with magic `BGPVPSL1`, then uses the journal's frame fields and CRC with an independent frame sequence and canonical JSON payloads. Each payload is a complete version of one `(client, session_epoch, peer_key, peer_up_generation, view, afi, safi)` object and contains: `state_version`, `journal_seq`, `observed_at`, negotiated `add_path`, `add_path_source`, `local_as`, `local_ip`, `peer_up_received_at`, `dump_started_at`, nullable `eor_received_at` and `eor_journal_seq`, nullable `peer_down_received_at` and `peer_down_journal_seq`, `last_received_at`, and `state` (`syncing`, `synced`, or `down`). `state_version` starts at 1 and increments on every replacement; prior versions remain in the log.

A Peer Up creates all expected-family objects for the view named by its header before that Peer Up is applied to derived state. The first configured-view Route Monitoring message for another view creates that view's objects with the same generation and marks `peer_appeared` in its interval. EoR and Peer Down append new object versions immediately. Peer Down closes every view/family object of the generation and removes that generation's paths from every derived view. Session loss writes `session_end` to the session journal but does not fabricate Peer Down fields or BGP withdrawals.

The `peer_state.log` writer appends and fsyncs on Peer Up, Peer Down, EoR, and immediately before any segment publication that relies on the state. `last_received_at` is checkpointed at segment close rather than on every UPDATE, bounding writes to peer events plus one version per active object per segment. A crash may leave a partial final frame. Recovery retains the valid prefix, saves any torn suffix as `peer_state.torn`, and rebuilds missing or inconsistent versions from the journal parts; `writer_restart` or `journal_corrupt` prevents a false `complete`.

`session.json` exists before the first accepted frame and records client, epoch, source IP, start time, Initiation metadata, journal path, counters, and `end=null`. It is atomically replaced at each segment close and at session close with end reason, frame count, and a `journal_parts` array that carries, per part, its file name, size, SHA-256, and first and last sequence. A single journal size and hash is not enough once the journal rotates, because `verify` and retention both work per part. The closed record never changes afterwards: whether a part has expired is stated by that part's own tombstone file, which retention writes beside it, and the catalog's `sessions` row is derived from the session record plus those tombstones rather than by editing either. The open JSON has no catalog row; only a closed session is appended to Parquet. A crash therefore leaves an attributable open session which recovery closes with `writer_restart`.

`gaps/<collector>/<gap_id>.json` is one canonical JSON object per continuous half-open gap. `gap_id` is SHA-256 over `collector|stream|kind|start_receive_at|reason|session_epoch`, with timestamps rendered as `<seconds>.<six-digit-micros>`. `session_epoch` is the epoch of the session that owned the collector when the gap opened, and `0` when no session was active, so two gaps that start at the same instant with the same reason cannot collide and one gap never has two ids. The object contains `end_receive_at=null` while active. Opening writes and fsyncs a temporary file, renames it, and fsyncs the directory; closing atomically replaces it. A cause change closes the old range and opens a new one, so ranges never overlap. A gap closes at the first event that applies to its stream. For an updates gap that is one of five: the first configured-view record for the same collector after the gap start, a peer of that view reaching `synced`, the close or replacement of the session that owned it, removal of the view or client by reload, or `gap_max_age` elapsing without coverage. A `kind=missed` RIB gap closes only at the next RIB cutoff or at removal, because a record or a sync says nothing about a snapshot that was never produced. The record and sync cases also open the segment that covers the range from that instant onward, so the gap and the segment meet exactly and neither a hole nor an overlap is left between them. `verify` checks that every gap object's end equals the `T` of the `TRANSITION` that closed its range, so the gap objects and the coverage timeline cannot disagree. A close event always has a receive time at or after the gap's start, because the watermark is monotonic per client and a session that would move it backwards is closed rather than archived, so `end_receive_at` can never precede `start_receive_at`. A close by `gap_max_age` opens a successor gap at the same boundary, so coverage accounting stays continuous and no range is silently uncovered; `gap_max_age` defaults to twice that view's `updates_interval`. `stale_gap` is a gap that has stayed open longer than `gap_max_age`, which is reachable precisely because the age close is what has not happened yet. Active gaps are read from sidecars; only closed gaps enter Parquet.

## 7. Segment transaction, publication, and crash recovery

Every open segment has a transaction record and temporary files under `work/<transaction_id>/`. `transaction_id` is SHA-256 over `collector|stream|name_minute_or_interval_start|ordinal|session_epoch`, with integers in decimal and timestamps in the sidecar format. At open the record fixes only that base identity and the first journal sequence. Before publication it is atomically extended with the cutoff, last sequence, state, reasons, final paths, and `finalized=true`. The final sidecar is built from journal-derived facts; its absence during active writing is normal.

Finalization performs these steps in order:

1. Stop assigning records to the segment at its receive-time cutoff, finish the gzip stream, and compute its byte count and SHA-256.
2. Re-read and hash the temporary MRT, build the final sidecar with all reasons and journal bounds, fsync both files, then atomically update and fsync the transaction with the final state, paths, hashes, and `finalized=true`.
3. Rename the sidecar to its final collector path and fsync that directory. A final sidecar without its MRT and with a live transaction is `pending`, not `missing`.
4. Rename the MRT to its final collector path and fsync the directory. This rename is the publication commit; it is the first point at which a RouteViews glob can see the segment.
5. Submit the sidecar row to the catalog appender, wait for its Parquet acknowledgement, then fsync and remove the transaction record and work directory.

A pre-publication hash mismatch or output write/fsync failure quarantines the segment, and the order is chosen so that no crash point contradicts itself:

1. Build the withheld sidecar in `work/<transaction_id>/` with `state=withheld` and one `withheld_reason` from the closed set `hash_mismatch`, `fsync_failed`, `write_failed`, `journal_corrupt`, and fsync it.
2. Set the transaction state to `quarantined`, with that sidecar's hash and final quarantine path, and fsync the record. This is the commit point.
3. Move the artifacts and the sidecar to `quarantine/<transaction_id>/` and fsync the directories.
4. Submit the withheld row to the catalog appender.

Recovery treats steps 3 and 4 as idempotent completion of a `quarantined` transaction: an artifact already in quarantine is not moved again, and a row already acknowledged is not resubmitted with a different identity because the catalog is a keyed projection. A crash before step 2 leaves the ordinary `open` or `finalized` state, which is repaired by the normal path; a crash after step 2 can never rebuild the segment as partial. A quarantined transaction is never rebuilt, never re-quarantined and never catalogued twice; retention treats `quarantine/` like the raw lane. A protocol parse or ADD-PATH encoding failure instead finalizes the preceding valid records as partial; the offending PDU remains only in the journal and is not a `withheld` file. Quarantine is diagnostic, not coverage. After publication, a hash mismatch is `corrupt`; an expected MRT absent without a tombstone is `missing`. `verify` reports one or the other and changes nothing.

At startup, `run` reconciles transactions before accepting sockets. A committed pair with matching hashes only needs its missing catalog acknowledgement; a mismatch is reported as `corrupt` and blocks new ingest for operator repair. A `finalized=true` transaction remains authoritative even if its final sidecar has not been renamed: its MRT is regenerated or moved from work with the recorded name and hash, unless the journal range is unavailable, in which case it is quarantined as `journal_corrupt`. Only a `finalized=false` segment is discarded and rebuilt as partial with `writer_restart`. Recovery never continues a partial gzip stream or invents receive timestamps. The pending set is exactly the transactions in state `open` or `finalized`; `quarantined` is terminal and is excluded from repair, while its artifacts still count for ordinal allocation as stated in section 5.

For a session left open by a crash, recovery keeps the valid journal prefix, saves a torn suffix as `journal.torn`, appends `writer_restart`, and closes `session.json`. A sequence gap or CRC failure followed by later valid frames is `journal_corrupt`, forces partial output, and remains a `verify` finding. A recorded torn suffix repaired as `writer_restart` is clean after recovery. New epochs are allocated only after reconciliation, so a second session in the interval receives the next ordinal.

Retention never deletes an MRT alone. It first writes `tombstones/<collector>/<segment-file-name>.json` containing the segment identity, hash, deletion time, and reason, fsyncs it, then removes the MRT and leaves its sidecar and tombstone. Sidecar plus tombstone means intentionally expired. A closed `session.json` is immutable. Session journals expire per part under the same raw retention: each part is tombstoned as `journal.<n>.tombstone.json` with that part's name, size, SHA-256, first and last sequence, and deletion time, fsynced before the part is unlinked. The tombstone is the record: no closed `session.json` is edited to mention it, and the catalog derives part expiry from the tombstones. Replay across a range fails explicitly with `journal_expired` when a part in the range is gone, so a RIB is never derived from a gap in the journal that nobody noticed. The smaller `peer_state.log`, session metadata, gap objects, segment sidecars, and tombstones remain so catalog metadata can still be rebuilt. RIB replay is possible only while the referenced journal is retained.

## 8. Parquet catalog and rebuild contract

The catalog has five tables and is a projection, never the only copy of a fact. Every row carries `part_seq` (the monotonically increasing sequence of the part it was written in) and `row_version` (bumped per row version), and every table declares a key: `segments` (collector, stream, interval start, ordinal), `sessions` (client, epoch), `peer_state` (client, session epoch, peer key, generation, view, AFI/SAFI, state version), `gaps` (gap_id), and `peers` (client, peer key, epoch, generation). It is a keyed projection rather than a set: a part may repeat a key an earlier part already holds, a reader takes the row with the greatest part sequence and then the greatest state version, and the appender never rewrites a part. Resubmitting a row after a crash is therefore harmless, and a repeated key is a read-time tie broken by that rule rather than a `verify` finding. Because both tie-break columns are in the row, an external reader needs no knowledge of the part naming convention, and this query is the published definition of current state:

```sql
select * exclude (part_seq, row_version)
from read_parquet('archive/catalog/segments/**/*.parquet')
qualify row_number() over (
  partition by collector, stream, interval_start, ordinal
  order by part_seq desc, row_version desc
) = 1;
```

The same shape applies to the other four tables with their own key, and one table needs care: `peer_state` already carries `state_version` in its key, so its current row is selected by partitioning on `(client, session_epoch, peer_key, generation, view, afi, safi)` and ordering by `state_version desc`, not by including the version in the partition. The README ships all five queries. A single catalog appender owns every Parquet path. Parts are immutable: `catalog/<table>/YYYY.MM/YYYYMMDD.NNNNNN.parquet`, with the day taken from the row's primary event time and `NNNNNN` allocated as the next existing part for that table and day. A late row goes to a new part for its own event day. A flush sorts rows by full table key and writes schema version and bgpviews version as key-value metadata. Rebuild guarantees logical row equality, not byte-identical Parquet or identical crash-dependent part boundaries.

- `segments`: `part_seq` and `row_version` first, then collector, client, view, feed (`bmp` or `bgp`), `local_as_true` (the configured local AS, which differs from the encoded envelope field only when the latter had to carry AS_TRANS), stream, interval start and end, ordinal, relative path, bytes, record count, compression, SHA-256, state (`complete`, `partial`, or `withheld`), sorted `partial_reasons`, nullable `withheld_reason`, `derived`, derivation version, session epoch, first and last journal sequence, cutoff receive time, first and last router timestamp, first and last receive timestamp, timestamp anomaly count, `late_arrival` count, and envelope-source identifier. Updates have `derived=false`; RIBs have `derived=true`.
- `sessions`: the closed `session.json` object, including client, epoch, source IP, Initiation sysName and sysDescr, start and end, end reason, journal identity, and counters such as `unconfigured_view` by view.
- `peer_state`: every version from every `peer_state.log`, keyed by session epoch, peer key, Peer Up generation, view, AFI/SAFI, and state version. Readers selecting current state take the greatest state version within the required epoch and generation, never a row from another session.
- `gaps`: every closed gap object, including kind (`gap` for updates, `missed` for RIBs), collector, stream, start, end, reason, and related epoch where one exists.
- `peers`: an optional roll-up of `peer_state` containing the latest object per client and peer key, its feed, epoch and generation, views, capabilities, and last state. `feed` is provenance rather than identity: it never joins the key, because a collector keeps its name and interval grid when the transport under it changes. It is derived only from `peer_state`, never from UPDATE PDUs, so peers visible solely through Peer Up, EoR, statistics, or Peer Down remain representable.

`rebuild-index` reads segment sidecars and tombstones, closed session objects, `peer_state.log`, and gap objects, then replaces catalog parts as a single-writer operation. With `--with-peers` it recomputes `peers` from those state rows. Expired raw journals are not needed for metadata rebuild, but any attempt to regenerate route data or a RIB without its journal fails explicitly rather than guessing.

`verify` checks both directions: names and ordinals, JSON schemas, CRC chains and sequence contiguity, segment and journal hashes, sidecar/tombstone/transaction reconciliation, and catalog rows against source objects. `missing`, `corrupt`, `journal_corrupt`, `stale_gap`, an `orphan`, and a transaction stuck in `open` past two intervals are findings and exit 1, where an `orphan` is a collector MRT or sidecar with no transaction, no sidecar and no catalog row describing it on any path. A durable `peer_state` version that is not yet projected is `pending` and is not a finding. A normal expired segment and a reconciled partial segment are clean. `verify` does not repair or relabel files; startup recovery and `rebuild-index` are the only writers of repair state.

## 9. Timestamp rule

Coverage and completeness are defined in sections 5.4 and 5.5. This section defines only how a record is timestamped and how an anomaly is recorded; it adds no coverage rule. The promise is deliberately narrower than "the router sent everything": `complete` means the retained journal is contiguous for the segment, every record that was placed in it at publication was encoded, and no recorded peer or session condition makes coverage incomplete. A record that was placed in the segment because its own interval had already closed is accounted for by `late_arrival` and is not a completeness condition, since its accounting interval is covered by the interval it belongs to. `complete` is a claim evaluated at publication over the records placed in the segment, and it is never revised: a record that arrives after publication and belongs to a published interval is placed in the open segment, counted in `late_arrival`, and reported by `verify` as a note rather than by rewriting the earlier sidecar. A published file is immutable, so the alternative would be to leave the archive with a claim that changes under the reader. BMP has no sequence number or acknowledgement in its common header (`refs/bgpkit-parser/src/parser/bmp/messages/headers.rs:40-77`), so exporter loss before bytes reach TCP is undetectable. `complete` can never prove the absence of such silent loss, of an unreported peer, or of a view the router never exposed. This limitation appears in `status` and the README.

Segment ranges are half-open `[start,end)` in receive time and, in the steady state, coincide with an interval. Two things are decided per record and they can differ: its accounting interval is the interval containing its `receive_at`, and its placement is the interval whose file it enters. For a record whose accounting interval is still open the two are the same. A record whose accounting interval is already closed enters the segment that is open when the record is routed, keeps its own timestamp, and increments that segment's `late_arrival` count. Both halves are sequence-decidable and therefore reproducible after a crash: a segment's sidecar records `first_journal_seq` and `last_journal_seq`, closure happens only at a journal sequence boundary, and replay places each frame by the sequence range that contains it, so no close event is needed in the journal and no record can land in two segments. The MRT record preserves the original router seconds and microseconds. If router time is zero or `abs(router_at-receive_at)` exceeds `skew_tolerance`, the segment gets `timestamp_anomaly` and increments its anomaly count. The journal always retains both timestamps for every frame, so no per-anomaly sidecar array is needed. Once a segment is finalized, its file never accepts an append and is never reopened. That is a statement about one file, not about one interval: an interval may hold several segments, because a session that ends and a new session that starts in the same interval write the next ordinal, and each of those is a new file created under the rule in section 6 rather than a reopen. This is a rule about file placement, not about timestamps: `receive_at` is assigned once per frame before routing and is never rewritten, and a record whose `receive_at` falls inside an already closed interval is appended to the currently open interval of that collector, keeps its own timestamp, and is counted in the open segment's `late_arrival` field. Nothing is clamped and no frontier is persisted, because receive time is assigned before a frame is routed and one frame can feed several collectors, so a per-collector correction could not be applied to it; placement is the only thing a collector owns. A closed interval is therefore closed to appends, never to the truth about when a record arrived, and a reader that selects records by timestamp must expect a segment to contain a small number of records outside its interval, all accounted for by `late_arrival`.

A segment's `complete` predicate is in section 5.5 and is not restated here. What this section adds is the one rule that feeds it: every peer event whose receive time falls inside a range must have added its reason to that range before the range closes, and an event exactly at a boundary belongs to the range beginning there. That rule is why a `Peer Down` inside a range can never leave the range `complete`.
`partial_reasons` is a closed set: `session_started`, `session_ended`, `view_removed`, `peer_syncing_at_open`, `peer_appeared`, `peer_restarted`, `peer_vanished`, `writer_restart`, `journal_corrupt`, `backpressure`, `disk_critical`, `timestamp_anomaly`, `receive_time_anomaly`, `clock_step_back`, `clock_step_forward`, `loc_rib_peer_ambiguous`, `capability_mismatch`, `peer_state_error`, `unsupported_peer_type`, `unsupported_message`, `vrf_not_supported`, `address_family_mismatch`, `mixed_add_path`, `mixed_family`, `as_width_unrepresentable`, `local_as_unknown`, `max_prefixes_exceeded`, `journal_expired`, `parse_error`, `encode_error`, `config_changed`, and `io_error`. Reasons are sorted lexicographically. Session edge reasons apply only strictly inside the interval. `peer_restarted` records a new generation for an existing peer; `peer_appeared` records a new peer or view. Simultaneous views alone add no reason.

`late_arrival` is a segment field, not a coverage reason: it counts records placed in the segment whose accounting interval was already closed. It does not make a segment partial, because the record is in a file and accounted for.

Gap reasons are the ones section 5.4's gap-opening calls return, `no_session`, `view_not_observed`, `view_removed`, and `peer_syncing_at_open`, plus the reasons that can stop all recording and therefore leave an interval with no record. Those appear in both lists because they are a property of the collector, not of one artifact: `no_session`, `view_not_observed`, `view_removed`, `peer_syncing_at_open`, `backpressure`, `disk_critical`, `writer_restart`, `clock_step_back`, `clock_step_forward`, `unsupported_peer_type`, `unsupported_message`, `vrf_not_supported`, `peer_state_error`, `address_family_mismatch`, `mixed_add_path`, `mixed_family`, `as_width_unrepresentable`, `local_as_unknown`, `max_prefixes_exceeded`, `journal_expired`, `parse_error`, `encode_error`, `config_changed`, and `io_error`. `capability_mismatch` is deliberately absent here: a refused Route Monitoring message is counted in `peer_state` and marks its open segment, but it never removes coverage, so it is never the reason an interval has no file. A gap means no updates file covers that range, so a gap and a segment never overlap.

A RIB is derived state at `cutoff_receive_at` and `cutoff_journal_seq`, not router-time ordering. It is `complete` only when its view was observed, its journal is contiguous from session start through the cutoff, every active object at the cutoff is synced in the current generation, and it has no partial reasons. RIB partial reasons are only `peer_syncing_at_snapshot` and `timestamp_anomaly`. Peer Down before the cutoff removes paths and does not by itself make the remaining snapshot partial.

A RIB interval with no output is `missed`, represented by a gap object with `kind=missed`, not an empty or fabricated RIB. Reasons are `worker_behind`, `writer_restart`, `disk_warning`, `disk_critical`, `no_session`, `view_not_observed`, `no_peer_up`, `unsupported_afi_safi`, `journal_corrupt`, `derive_error`, `io_error`, and `config_changed`. Only `complete` and `partial` MRT segments enter collector trees, and every partial segment of either stream carries `.partial`.

## 10. MRT encoding and RIB derivation

For an accepted type 0 UPDATE, peer AS, peer IP, peer BGP ID, and AS width come from the per-peer header. `local_as` comes from the current generation's sent OPEN My AS, reconciled with the Four-Octet-AS capability: when My AS is AS_TRANS (23456) and that capability carries a value, the capability value is used; when My AS is AS_TRANS and the capability carries nothing, the Peer Up is refused with `local_as_unknown` and the session closes, because every record of that session would otherwise be attributed to 23456. `local_ip` comes from that Peer Up's Local Address. For type 3, local and peer IP are `0.0.0.0`, AS width is 32-bit, and local AS comes from the fabricated sent OPEN. The BMP listening address and a wildcard bind address are never consulted. Interface index is synthesized as 0. If type 0 peer and local IP families differ, focl's encoder cannot build the envelope (`refs/focl/src/archive/snapshot.rs:60-69`); bgpviews records `address_family_mismatch`, preserves the frame in the journal, and closes the session instead of substituting an address.

AS width is not a storage preference. The BGP4MP subtype is the decoder contract for the bytes inside the record: subtypes 4 and 9 tell a reader that the encapsulated UPDATE uses four-octet AS_PATH encoding, and subtypes 1 and 8 tell it to use the legacy two-octet encoding. Storing a two-octet PDU under an AS4 label is the same class of mistake as storing ADD-PATH NLRI under a plain subtype: the reader decodes every AS in the path at the wrong width and reports nothing. Always storing 32-bit would therefore require re-encoding AS_PATH from two to four octets, which breaks the raw-copy invariant, puts bytes in the archive the router never sent, and reopens the AS4_PATH reconstruction ambiguity. The subtype follows the session's AS width, which is the router's choice, not ours.

What that leaves is a per-field question, and the two fields are not the same case.

- The peer AS must be read from the raw four-byte per-peer header field, not from the parser's value, because the parser discards the high two octets when the AS-size flag is set (`refs/bgpkit-parser/src/parser/bmp/messages/headers.rs:336-340`). A peer AS above 65535 in an A=1 session is a contradiction: a four-octet speaker must advertise the four-octet capability, so the session cannot be two-octet unless the peer is non-compliant or the header is wrong, and there is no truthful envelope for it because subtypes 1 and 8 give both AS fields one two-byte width (`refs/bgpkit-parser/src/parser/mrt/messages/bgp4mp.rs:303-307`). That Peer Up is refused with `as_width_unrepresentable` and the session closes.
- The local AS above 65535 in an A=1 session is normal: our router has a four-octet ASN and the peer is a legacy two-octet speaker. RFC 6793 puts AS_TRANS in AS_PATH for exactly this case, so the header field carries AS_TRANS (23456), which agrees with the encapsulated PDU, and the true local AS is recorded in the segment sidecar as `local_as_true` and in the catalog. Refusing here would discard perfectly archivable data; writing the true value into a two-byte field would truncate it (65536 becomes 0).

The updates writer encapsulates the complete original BGP PDU, including its 19-byte header, without re-encoding it. Every updates file uses BGP4MP_ET so router microseconds are retained. The subtype mapping is exact: 16-bit plain is 1, 16-bit ADD-PATH is 8, 32-bit plain is 4, and 32-bit ADD-PATH is 9. An UPDATE with no NLRI uses the plain subtype. If one UPDATE mixes families that require ADD-PATH and plain decoding, one BGP4MP subtype cannot describe the whole encapsulated message; bgpviews journals the PDU, writes no MRT for it, finalizes the preceding configured segment as partial with `mixed_add_path`, and closes the session. The parser's subtype-driven decode and consistency checks are at `refs/bgpkit-parser/src/parser/mrt/messages/bgp4mp.rs:37-61,268-299`.

A Route Monitoring or Peer Down message before its Peer Up or with an unknown generation is `peer_state_error`; malformed framing is `parse_error`. No envelope values are invented. Raw archival does not depend on re-encoding, but controlled decode is required for ADD-PATH selection, EoR, and RIB state. A decode or validation failure that prevents correct state application preserves the raw frame, writes no derived state for it, marks the configured segment partial, and closes the session.

The RIB worker holds one in-memory trie per `(session_epoch, view)`. Keys are `(peer_key, peer_up_generation, afi, safi, prefix)` for plain NLRI and the same key plus `path_id` for ADD-PATH. Announcements replace only the same key, withdrawals remove only that key, Peer Down removes every key for the generation, and a new Peer Up generation starts that peer empty. Replay applies these operations in journal sequence order and never sorts by router time.

A scheduled or SIGHUP-triggered RIB at receive cutoff T is executed by the session's single state owner at a journal sequence boundary: after every frame with `receive_at < T` and before the first frame with `receive_at >= T`, and always expressed in journal sequence order, because replay order and interval order are both sequence order and a receive-time comparison alone would be ambiguous after a clamped regression. Its sidecar stores the resulting sequence cutoff. It does not require an updates segment to close and works for off-boundary requests. Live RIB production after process restart still waits for a new session and a new initial dump; journal replay is used to repair segments and for explicit retained-history backfill, not to resume an old live trie invisibly.

RIB output uses TABLE_DUMP_V2 with a peer index table. The index contains every active peer generation in the view, sorted by full peer key and generation, even when it has no route. Prefix records sort by address bytes and prefix length, then plain before ADD-PATH; entries sort by peer index and path ID, and sequence numbers start at 0. Separate plain and ADD-PATH records represent peers with different path-ID rules for one prefix. IPv4 unicast uses subtype 2 or 8 and IPv6 unicast uses 4 or 10 (`refs/bgpkit-parser/src/models/mrt/table_dump_v2.rs:38-50`). `record_count` includes the peer index record. More than 65,535 indexed peers makes the RIB `missed` with `derive_error`, matching focl's encoder bound. v1 derives RIBs only for these two families; any other expected family makes the interval `missed` with `unsupported_afi_safi`, because this parser rejects RIB_GENERIC decoding (`parser/mrt/messages/table_dump_v2/mod.rs:50-53`).

RIB `originated_time` is the last applied UPDATE's router seconds, including zero. A trie entry carries that UPDATE's anomaly flag, and a RIB gets `timestamp_anomaly` iff an emitted entry or an active object's EoR has the flag. The RIB common timestamp is the receive cutoff. Collector BGP ID is configured `bgp_id`, or if null is fixed for the session from the first Peer Up sent OPEN BGP identifier. View name is the collector view. The sidecar records that source and the synthesized interface index and view; local AS and local IP are observed from Peer Up.

`feed` defaults to `bmp`. Supported view blocks for a `bmp` client are `adj-in-pre`, `adj-in-post`, `loc-rib`, and `loc-rib-filtered`; Adj-RIB-Out has no supported block in v1. A `bgp` client accepts only `adj-in-pre`, requires `asn`, and rejects every other view block at `check` time rather than silently ignoring it. View cadence belongs to the client because collectors are client/view pairs. `bgp_id=null` selects the session-fixed Peer Up rule for a `bmp` client. A `bgp` client must set `bgp_id` explicitly, because it originates a BGP session and therefore must have its own identifier before any message exists; `check` refuses the configuration when it is null. The optional publisher has its own destination section and is disabled by default.

Every successful load by `run` writes the effective configuration to `config/<config_sha256>.toml` and fsyncs it, and `check` writes nothing at all, so it can be run against a serving archive without touching it; each segment sidecar records that hash, so replay, `rebuild-index` and RIB regeneration use the configuration that was in force when the segment was written rather than whatever the file says today. `check` validates and prints effective configuration, firewall rules, and router snippets. SIGHUP atomically applies a valid new file and schedules an immediate RIB using the normal cutoff rule. Removing a view closes its open segment with `config_changed`; later records for it become `unconfigured_view`. Adding a view affects only later records. Removing a client or revoking its current source closes the session with `config_changed` or `authorization_revoked`; an invalid reload changes nothing.

Router templates ship for FRR, Junos, Cisco IOS-XR, Nokia SR OS, and Arista EOS. Only the FRR gate is required in CI. Behavior of the other templates is UNVERIFIED until each release candidate applies the snippet to the named platform and captures Peer Up, initial dump, EoR, incremental updates, and Peer Down; release notes must distinguish that capture from an untested template.

## 12. Commands

- `bgpviews run --config FILE`: recover transactions, then ingest, derive, publish, and append catalog parts.
- `bgpviews check --config FILE`: validate and render effective configuration, router snippets, and firewall rules; exit 2 on invalid configuration.
- `bgpviews status --config FILE`: show the 30-day coverage timeline, session state and last-message age, per-generation peer dump and EoR state, view gaps and last segment reasons, worker backlog and errors, disk mode, and counters including `unconfigured_view`, `backpressure`, `missing`, `corrupt`, and `withheld`. Dead, idle, refused, replaced, and recovering sessions are distinct.
- `bgpviews verify --config FILE`: perform the read-only reconciliation in section 8 and print every finding.
- `bgpviews rebuild-index --config FILE [--with-peers]`: rebuild the catalog from persisted source objects; disaster recovery only.

Exit codes are 0 for clean, 1 for findings, 2 for configuration error, and 3 for I/O error. No other command or hidden state-changing endpoint exists.

## 13. Workers and failure handling

Ingest owns one session and its journal, MRT writers, peer-state transitions, and RIB mutation order. The RIB worker requests cutoffs from that owner rather than reading a concurrently changing trie. The catalog appender is the only Parquet writer. The retention worker alone writes tombstones and removes expired artifacts. The optional publisher copies only committed files and records destination success separately; publisher failure never rewrites coverage.

All queues are byte-bounded. If ingest cannot journal, encode, write, or submit within `backpressure_deadline`, it stops reading, records `backpressure`, closes the session, finalizes configured open segments as partial, and opens the corresponding gaps. TCP backpressure can expose congestion at this collector; it cannot reveal routes an exporter discarded before its socket. Whether FRR, Junos, IOS-XR, SR OS, or EOS drops BMP messages under queue pressure, and whether each emits EoR for every configured view and AFI/SAFI, is UNVERIFIED. The measurement is a controlled full-table feed with exporter queue counters and a packet capture at both ends; no `complete` rule assumes the answer.

At or below `disk_warning_free_percent`, new RIB derivation stops and intervals become `missed` with `disk_warning`; updates continue. At or above `disk_warning_resume_percent`, derivation resumes at the next interval. At or below `disk_critical_free_percent`, new sessions are refused and current sessions close; open updates become partial with `disk_critical`, gaps and missed RIBs use the same reason, and `status` reports `degraded`. Normal operation resumes only at or above `disk_critical_resume_percent`. The guard never deletes unexpired data, never drops a record to relieve pressure, and has no `overflow` state.

An actual write or fsync failure uses `io_error` when it cannot be attributed to a watermark. The socket closes and recovery waits until writes are possible; a sidecar that cannot be written is not claimed to exist. Catalog acknowledgement failure pauses further publication and applies backpressure while already committed MRT/sidecar pairs remain recoverable. A router reconnect receives a new epoch, and its trie starts empty. Session loss never synthesizes withdrawals or Peer Down.

## 14. Transport and authorization

Routers dial out; bgpviews never dials a router. Each client has one listening port and a source-IP allowlist. The port is demultiplexing, not authentication, and the source address is the only v1 credential. Initiation sysName and sysDescr are evidence, not identity. Every session records its actual source and epoch so a bad feed can be quarantined without confusing it with another client.

A connection from an unlisted source is refused and logged once per refusal, not per packet. A replacement connection from an authorized source closes the old session as `replaced_by_newer` before the new epoch starts. Statistics Reports can serve as observed heartbeat when present, but silence alone is not called peer loss. TLS, TCP-AO, route mirroring, and vendor-specific authentication extensions are outside v1.

The first BMP message must be Initiation as required by RFC 7854 section 3.3; otherwise the session closes with `parse_error`. Route Mirroring is journaled and then refused with `unsupported_message`, never converted into updates. An unrecognized BMP message type is skipped by its declared length and counted, never a session close, because RFC 7854 section 4.1 requires an implementation to ignore types it does not understand; only a framing failure or a checksum mismatch is `parse_error`. The parser accepts only BMP version 3 (`refs/bgpkit-parser/src/parser/bmp/messages/headers.rs:62-77`). A version 4 connection is refused at the common header with `unsupported_bmp_version`; there is no attempt to archive it with missing metadata. Parser issue #362 tracks that format dependency.

## 15. Non-goals for v1

RD and Local peer types 1 and 2, non-global Loc-RIB instances and other VRFs, Adj-RIB-Out output, route mirroring, BMPv4-specific handling, non-unicast RIB derivation, Parquet route-data sidecars, multi-tenant hosting, an on-disk incremental RIB chain, and, for the BGP feed, route announcements, route-server behaviour, outbound policy and route-refresh-driven re-dumps are non-goals. Refused BMP peer types are visible failures, not records silently reassigned to another view. ADD-PATH, global Adj-RIB-In pre/post, and global Loc-RIB filtered or unfiltered are in scope.

## 16. Acceptance tests
Each item is an executable gate with synthetic BMP captures where a router behavior cannot be scheduled deterministically.


1. One FRR session produces updates whose prefixes and AS paths match the sent routes in monocle and, as a manual third-party gate, bgpdump. The test reads the actual final file path and a shell-expanded set of paths, not a directory argument.
2. Simultaneous pre-policy and post-policy records land in separate collector trees, a file may contain multiple peer address families or AS widths but only one view, and an unconfigured-view frame is present only in the journal and counted in `status`, with no dropped-record field or coverage demotion.
3. Kill the process mid-interval. Restart publishes the recovered segment as `.partial` with `writer_restart`, writes the second session as `.partial.2` or `.2` according to its own state, reconciles the old session, and leaves `verify` clean.
4. Break BMP for two intervals. Non-overlapping `no_session` gaps cover the outage, affected RIB intervals are `missed`, and a new epoch re-anchors the trie without withdrawals invented for the old session.
5. Delete catalog parts and run `rebuild-index`; segments, sessions, peer_state, and gaps match their source rows logically. With `--with-peers`, the roll-up matches a fold of `peer_state.log`, including a peer with Peer Up and Peer Down but no UPDATE.
6. Truncate a published file and `verify` reports `corrupt`; remove it and its tombstone and `verify` reports `missing`; expire it normally and `verify` accepts the sidecar plus tombstone. None of these cases is relabeled `withheld`.
7. Refuse an unlisted source once, then show dead, idle, refused, and replaced sessions as different `status` states.
8. With the #363 parser fix, an ADD-PATH peer writes subtype 8 or 9 according to AS width and a RIB with two path IDs for one prefix; a 16-bit plain peer writes subtype 1 and a 32-bit plain peer writes 4 in the same run. A mixed-family ADD-PATH UPDATE stays in the journal and closes with `mixed_add_path` rather than malformed MRT.
9. Two Peer Down/Up cycles in one BMP session replay in journal order, remove the old generation's paths, produce `peer_vanished` and `peer_restarted`, and never accept the first generation's EoR for the second.
10. At the warning watermark updates continue and RIBs are `missed` with `disk_warning`; at the critical watermark sessions close and open updates are partial with `disk_critical`; resume occurs only above the configured resume thresholds, and no `overflow` value exists.
11. A zero, late, and skewed router timestamp each lands by receive time with its original MRT timestamp, increments `timestamp_anomaly`, and never appends to a closed interval. A RIB cutoff follows journal order rather than those timestamps.
12. Type 1, type 2, and nonzero-distinguisher type 3 captures are refused without global MRT output. Type 3 F=0 and F=1 use their own collectors, both OPEN and Local Address rules are enforced, and a type 0 address-family mismatch has no substituted envelope address.
13. Crash at each publication step, including after sidecar rename and after MRT commit. Recovery either finishes the same transaction or rebuilds from the journal, never exposes a sidecar-less committed segment, and emits no duplicate ordinal.
14. Two emulated Loc-RIB peers that differ only by family keep separate peer keys and neither empties the other's trie; a repeat Peer Up for a live key starts a new generation, resets that generation's trie, and leaves the other instance untouched.
15. Kill after journal fsync and before any transaction exists for that range: recovery rebuilds it as `.partial` with `writer_restart`, not a silent hole.
16. Submit the same catalog row twice after a simulated crash: one logical row is read, and `verify` reports no duplicate-key finding.
17. Step the clock backwards across a restart: the persisted watermark keeps assignment monotonic, and a step past `clock_step_back_tolerance` closes the session with `clock_step_back`.
18. An FRR neighbor configured with `feed = "bgp"` produces an `adj-in-pre` collector whose prefixes and AS paths match what that router advertises in monocle, and match the same router's BMP pre-policy collector for the same interval within the session's first full table. Dropping the session writes `session_ended` and a gap, and reconnecting starts an empty trie rather than inheriting the old one.
19. Two Loc-RIB emulated peers in one session, one filtered and one not, over the same families, keep separate keys and separate tries, and a Peer Down with F=0 closes only the unfiltered instance. Separately, two same-F instances that differ by family make a Peer Down ambiguous: both close and the views are marked `loc_rib_peer_ambiguous`.
20. Kill the process mid-interval, restore a clock that is behind the journal's last receive time, and confirm startup recomputes the watermark from the journal tail: no frame is assigned below the journaled maximum and no interval is reopened.
21. Expire one journal part of a multi-part session under retention: the per-part tombstone is accepted by `verify`, the remaining parts still replay, and a RIB that needs the expired range fails with `journal_expired` instead of being derived from a hole.
22. Two A=1 cases, treated differently: a peer AS above 65535 in the per-peer header refuses the session with `as_width_unrepresentable`, while a local AS above 65535 encodes AS_TRANS in the envelope, records the true value in `local_as_true`, and archives the segment; the catalog row and the sidecar agree on the real local AS.

## 17. Fixed decisions and open measurements

The fixed product decisions are the bgpviews name, bgpviews.org, MIT license, one binary plus `bgpviews-core`, `bgpviews.toml`, `BGPVIEWS_` environment prefix, default root `/var/lib/bgpviews`, separate pre/post collectors, per-message view routing, Parquet catalog with JSON source sidecars, five commands, in-memory live RIBs with no on-disk chain, v1 ADD-PATH including MRT ADDPATH subtypes, no telemetry or accounts, and parser dependencies for BMPv4 and ADD-PATH rather than local parsing workarounds.

A BGP peering feed exists beside BMP, with one view, no announcements and no policy, because a router that cannot export BMP would otherwise have no path into the archive at all. The fixed mechanism decisions new to this version are receive-time interval membership, a raw ordered BMP journal, epoch- and generation-scoped peer-state logs, no view-switch inference, Peer Up as the local envelope authority, transaction-based crash rebuild, one partial/ordinal filename grammar, and explicit separation of unconfigured exclusion, pre-publication withholding, post-publication corruption, and absence.

Open work is measurement, not undecided file behavior: parser #363 must demonstrate per-family ADD-PATH decode; each vendor template needs its capture; exporter queue loss and per-view EoR behavior need controlled captures; third-party discovery of suffixed names needs a crawler test; and a real ADD-PATH full table must measure journal write throughput, storage amplification, RIB size, and memory. Until those measurements are run, no vendor behavior, capacity target, or external crawler compatibility is claimed.

## 18. Implementation questions

These are open by nature and are answered by code and measurement, not by more prose. They are recorded here so an implementer knows which decisions are still theirs.

- **Vendor BMP behaviour.** Only the FRR gate is exercised in CI. Junos, IOS-XR, SR OS, and EOS templates are unverified until each produces a capture: their Initiation fields, their stats-reporting period, and whether they send an EoR per family. Any of them may turn out not to send one, which leaves those intervals `partial` with `peer_syncing_at_open` and is visible rather than silent.
- **Parser #363.** ADD-PATH decoding for BMP Route Monitoring is blocked on bgpkit-parser issue #363. Until it lands, an ADD-PATH peer is refused rather than mis-decoded, and `mixed_add_path` records why.
- **RIB completeness under backpressure.** A snapshot taken while a peer is mid-dump is `partial` with `peer_syncing_at_snapshot`. Whether that is common enough on a busy router to justify a retry heuristic is a measurement, not a rule.
- **Empty-segment volume.** An always-on collector writes one empty updates file per interval per silent view. At a 15-minute interval that is 96 small files a day per collector. If that turns out to be a real operational cost, the fix is a configurable minimum, not a different coverage model.
- **Retention interaction.** Tombstones make expiry auditable, but nothing in this document decides whether an expired segment's range should be re-labelled `expired` or left as `segment` with a tombstone. The archive reads correctly either way; the choice is cosmetic and belongs in code.
